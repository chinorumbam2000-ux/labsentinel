# LabSentinel — full-stack deployment on Render

Status: **prepared and validated locally, not deployed.** Nothing has been
provisioned or purchased. Synthetic data only.

The deployment is described by [`render.yaml`](../render.yaml) (a Render
Blueprint, validated against Render's published JSON schema). The public
GitHub Pages site — the frozen classroom demo built from `main` in Local Demo
Mode — is separate and stays untouched as the stable fallback.

## 1. What gets deployed

| Resource (render.yaml) | Type | Source | Notes |
|---|---|---|---|
| `labsentinel-db` | Render Postgres 16 | — | Region `oregon`; database `labsentinel`, user `labsentinel`; credentials generated by Render |
| `labsentinel-api` | Web service, Docker | `backend/Dockerfile`, branch `capstone-development` | Start command `python -m app.serve`; health check `/api/health` |
| `labsentinel` | Static site | `npm ci --include=dev && npx vite-node scripts/check-render-env.ts && npm run build` → `dist/` | Branch `capstone-development`; SPA rewrite `/*` → `/index.html` |

```
 browser ──HTTPS──► labsentinel (static site, React, API Capstone Mode, base path /)
    │
    ├──HTTPS──► labsentinel-api (FastAPI container, APP_ENV=presentation)
    │              CORS: exactly the static site's https origin
    │              └── private network ──► labsentinel-db (Postgres 16)
    │
    └──HTTPS──► launch.smarthealthit.org (SMART sandbox: public client, PKCE, no secret)
```

The API and database are in the same region, so the API reaches the database
over Render's private network (`fromDatabase` → internal connection string).

## 2. Environments

| | development | presentation (Render) | production-like |
|---|---|---|---|
| `APP_ENV` | `development` | `presentation` | `production` |
| Development-only endpoints | on | **on only with `DEMO_ENDPOINTS_ENABLED=true`** | always off; the flag is **rejected at startup** |
| CORS methods | GET, POST | GET, POST only when the flag is on | GET only |
| `FHIR_PSEUDONYM_SALT` | development default | own secret — **required** (startup refuses the development default when the flag is on) | own secret |
| `app.demo.reset` / `prepare` | allowed | allowed | refused |

The Render Blueprint uses **presentation with the flag on**, because the live
demonstration needs FHIR ingestion, recalculation, the evaluation page and
readiness. Those endpoints have **no authentication**: share the site only
for the presentation and recruiting period, then set
`DEMO_ENDPOINTS_ENABLED=false` (the site keeps working read-only).

### Endpoint gating (verified with the Docker image, all three configurations)

| Endpoint | Public read-only | Presentation + flag | Presentation, no flag / production |
|---|---|---|---|
| `GET /api/health`, `/api/health/database` | ✓ | ✓ | ✓ |
| `GET /api/facilities`, `/api/observations`, `/api/signals`, `/api/demo/*` | ✓ | ✓ | ✓ |
| `GET /api/surveillance/dynamic/*`, `/api/statistics/ewma*`, `/cusum*`, `/comparison` | ✓ | ✓ | ✓ |

SMART sandbox helpers run in the browser (the `fhirclient` library against the

## 3. Environment variables

### API (`labsentinel-api`)

| Variable | Value in render.yaml | How it is set |
|---|---|---|
| `APP_ENV` | `presentation` | Blueprint |
| `DEMO_ENDPOINTS_ENABLED` | `true` | Blueprint (turn off after the presentation period) |
| `DATABASE_URL` | Render Postgres internal connection string | `fromDatabase` (never typed by hand). Render's `postgresql://` form is pinned to the psycopg 3 driver automatically; any other driver is rejected |
| `DATABASE_CONNECT_TIMEOUT` | `10` | Blueprint |
| `FHIR_PSEUDONYM_SALT` | random 256-bit value | `generateValue` — never committed |
| `FHIR_MAX_REQUEST_BYTES` | `1000000` | Blueprint |
| `MIGRATE_ON_START` | `true` | Blueprint (see §5) |
| `CORS_ORIGINS` | the static site's https origin, e.g. `https://labsentinel.onrender.com` | **Dashboard, once** (`sync: false`) |
| `PORT` | injected by Render | automatic |

### Static site (`labsentinel`) — build time, compiled into the public bundle

| Variable | Value | How it is set |
|---|---|---|
| `NODE_VERSION` | `20` | Blueprint |
| `LABSENTINEL_BASE_PATH` | `/` | Blueprint (GitHub Pages keeps its default `/labsentinel/`) |
| `VITE_DATA_SOURCE` | `api` | Blueprint |
| `VITE_API_BASE_URL` | the API's https URL, e.g. `https://labsentinel-api.onrender.com` (no trailing slash, no path) | **Dashboard, once** (`sync: false`) |
| `VITE_SMART_ENABLED` | `true` | Blueprint |
| `VITE_SMART_CLIENT_ID` | `labsentinel-capstone-sandbox` (public identifier, not a secret) | Blueprint |
| `VITE_SMART_SCOPES` | `openid fhirUser patient/Observation.rs` | Blueprint |
| `VITE_SMART_REDIRECT_URI` | empty (the app derives `https://<site>/smart/callback` at run time) or exactly `https://<site>/smart/callback` | Dashboard, optional (`sync: false`) |

**Why two values are entered by hand.** The public `*.onrender.com` URLs do
not exist until Render creates the services, and a Blueprint can reference
another service only by its *internal* host, not its public HTTPS URL. So
`VITE_API_BASE_URL` and `CORS_ORIGINS` are entered once in the Dashboard; they
are not guessed in the repository.

**Build guard.** `scripts/check-render-env.ts` runs before the static build
and **fails the deploy** if `VITE_DATA_SOURCE` is not `api`, if
`VITE_API_BASE_URL` is missing, not https, local (`localhost`, `127.0.0.1`) or
a placeholder, if the base path is not `/`, if the SMART redirect URI is set
but is not an https `/smart/callback` URL, or if any `VITE_*` variable looks
like a secret. A misconfigured site is therefore never published.

No secret appears in `render.yaml` or in this document: database credentials
come from `fromDatabase`, the salt from `generateValue`, and the two public
URLs from the Dashboard. The SMART client is public (PKCE): there is no client
secret, and none may be added.

## 4. HTTPS, CORS and SMART

- Render serves the static site and the API over HTTPS; the build guard
  rejects an `http://` or local API URL, and the frontend therefore never
  calls `http://127.0.0.1` or `localhost`. (Those strings remain in the bundle
  only as the local-development default and a validation rule; a browser run
  against a root-path build contacted only the site, the configured API and the
  map tile servers.)
- `CORS_ORIGINS` must be **exactly** the static site's origin (scheme + host,
  no path, no trailing slash). Wildcards are rejected at startup. Outside
  development, the readiness checklist reports **FAIL** for an empty, `http`
  or localhost origin.
- SMART: the redirect URI is `https://<static-site-host>/smart/callback` and the
  launch URL `https://<static-site-host>/smart/launch`. The SMART Health IT
  sandbox accepts any redirect URI for a public client, so nothing has to be
  registered there; for the sandbox's EHR-launch tool, enter the launch URL
  above as the app's launch URL.

## 5. Migrations

`python -m app.serve` (the Blueprint's start command) runs
`alembic upgrade head` **once, before the server binds the port**, when
`MIGRATE_ON_START=true`, then serves on `0.0.0.0:$PORT`. So:

- no request is ever served by a half-migrated database (the health check only
  passes after migration);
- nothing runs per request; a restart at head is a no-op (verified: no upgrade
  runs and no data changes);
- it never seeds, resets or prepares data;
- it works on every plan, including free (where Render's pre-deploy command is
  not available). On a paid instance you may instead set a **Pre-Deploy
  Command** `alembic upgrade head` and `MIGRATE_ON_START=false`.

The image's default command (plain `uvicorn`, used by `docker run` locally)
never migrates.

## 6. Demonstration data (one time)

A new database is empty. The classroom seed and the presentation data are
loaded **once**, explicitly, with the existing safe commands — never on
container start. Free web services have no Render Shell, so run them from your
own machine against the database's **External Database URL** (Render
Dashboard → `labsentinel-db` → Connect → External). Use the **same salt and
CORS origin as the API** so the final readiness check matches the service.

Windows PowerShell, from `backend\` with the project's virtual environment:

```powershell
$env:APP_ENV = "presentation"
$env:DEMO_ENDPOINTS_ENABLED = "true"
$env:DATABASE_URL = "<External Database URL>?sslmode=require"     # secret: paste, never commit
$env:FHIR_PSEUDONYM_SALT = "<the API's FHIR_PSEUDONYM_SALT>"      # Dashboard → labsentinel-api → Environment
$env:CORS_ORIGINS = "https://<static-site-host>"
.\.venv\Scripts\python -m app.seed                   # frozen Day 1-5 classroom demo (idempotent)
.\.venv\Scripts\python -m app.demo.prepare           # dynamic dataset, Composite/EWMA/CUSUM, checks → READY
.\.venv\Scripts\python -m app.seed.smart_sandbox     # optional: SMART sidecar ingestion bridge
Remove-Item Env:DATABASE_URL, Env:FHIR_PSEUDONYM_SALT   # do not leave secrets in the shell
```

`app.seed` is idempotent. `app.demo.prepare` verifies the database, the
migrations and the frozen seed first and refuses to repair serious problems;
it then clears live-demo leftovers and restores the dynamic dataset (a reset of
presentation data only — never the classroom demo or the evaluation results).
Run `prepare` again before each presentation to remove the previous run's FHIR
ingestion.

After preparation, restrict the database's inbound access (Dashboard →
`labsentinel-db` → Networking) — the API uses the private network and needs no
public access. Re-open it only when you need to run the commands again.

## 7. Readiness

- `https://<api>/api/health` → `{"status":"healthy", …}` (liveness; Render's
  health check).
- `https://<api>/api/health/database` → database reachable.
- `https://<api>/api/readiness` → the full checklist (environment, **CORS
  origin**, database, migration head, frozen seed parity, facilities, FHIR
  fixtures dry run, dynamic engine, EWMA, CUSUM, evaluation artifact
  checksums, SMART bridge). Must say **READY**. It reports no connection
  string, host, password, salt or token.
- `https://<site>/overview` → **Presentation readiness** panel: the same
  checklist plus the frontend's own configuration.

## 8. Render deployment — step by step

Nothing below has been done yet; each step is yours to take.

1. **Render account.** Sign in at <https://render.com> (GitHub sign-in is
   simplest).
2. **Connect GitHub.** Authorise Render for the `labsentinel` repository.
3. **Blueprint.** Dashboard → **New** → **Blueprint** → choose the repository.
4. **Branch.** Select **`capstone-development`** (the file is `render.yaml` at
   the repository root; each service also pins that branch).
5. **Review resources.** Render lists `labsentinel-db`, `labsentinel-api` and
   `labsentinel`, all on the **free** plan (§10). Render prompts for the
   `sync: false` values: `CORS_ORIGINS`, `VITE_API_BASE_URL`,
   `VITE_SMART_REDIRECT_URI`. Their final values are not known yet — leave them
   empty (or, if Render insists, enter `https://pending.invalid`; the build
   guard will stop the static site until you replace it). Apply.
6. **PostgreSQL.** `labsentinel-db` is created (Postgres 16).
7. **API.** `labsentinel-api` builds from `backend/Dockerfile`, migrates to the
   head on start and passes `/api/health`. (The static site's first build
   fails at the guard — expected until step 9.)
8. **Backend URL.** Copy the API's URL from its page, e.g.
   `https://labsentinel-api.onrender.com` (yours may differ). Check
   `<API URL>/api/health`.
9. **Frontend API URL.** `labsentinel` → Environment → `VITE_API_BASE_URL` =
   that URL (https, no trailing slash). Save (do not deploy yet).
10. **CORS.** Copy the static site's URL, e.g. `https://labsentinel.onrender.com`.
    `labsentinel-api` → Environment → `CORS_ORIGINS` = that origin. Save and
    let the API redeploy.
11. **SMART redirect.** Leave `VITE_SMART_REDIRECT_URI` empty (the app uses
    `https://<site>/smart/callback`), or set exactly that URL. No sandbox
    registration is needed.
12. **Migrations.** Already applied by the API start (step 7); the API log
    shows `Schema at Alembic head 0007`.
13. **Demonstration data.** Run §6 once from your machine.
14. **Readiness.** Open `<API URL>/api/readiness` → **READY** (SMART bridge may
    be WARN if you skipped `smart_sandbox`).
15. **Static site.** `labsentinel` → **Manual Deploy** → *Deploy latest
    commit*. The build guard must print `Render build configuration OK`.
16. **Public URL.** Open `https://<site>/overview`: *API Capstone ● Connected*,
    the readiness panel READY. Open a deep link such as
    `https://<site>/evaluation` directly and refresh — it must load, not 404.
17. **Presentation walkthrough.** Run the ten steps in
    [presentation-guide.md](presentation-guide.md) end to end with
    `?presentation=true` (step 8 reaches the live SMART sandbox). Then run
    §6's `app.demo.prepare` again so the next audience starts clean.

## 9. Auto-deploy

**Off** for both services (`autoDeployTrigger: "off"`): pushing to
`capstone-development` never changes the live site during the submission
period. Deploy deliberately with **Manual Deploy** after the change has passed
the test suite and the walkthrough. (Render may still offer to sync Blueprint
edits; review them before applying.)

## 10. Free vs paid

Render's plans and limits change; check <https://render.com/pricing> and the
free-tier documentation before relying on any of the following, which reflects
Render's published terms at the time of writing.

| Resource | Free is fine for | Limits that matter for a live presentation |
|---|---|---|
| Static site | everything | none significant |
| Web service (API) | testing, rehearsals | **spins down after ~15 minutes idle**; the next request waits for a cold start (up to about a minute), during which the site shows *API Capstone ● Unavailable*. No Shell, no pre-deploy command, limited monthly free instance hours |
| Postgres | testing | **free databases expire** (about 30 days after creation, with a short grace period to upgrade) and have small storage; not for anything that must survive the grading period |

**Recommendation.** Keep everything free while testing. For the presentation
and the recruiter/grading window, temporarily upgrade:

- `labsentinel-api` → **Starter** (always on: no cold start mid-demo);
- `labsentinel-db` → **Basic-256mb** (no expiry).

Both are low monthly costs (check current pricing) and can be downgraded or
deleted afterwards. If you stay on free, open the site a few minutes before
presenting to wake the API, and keep the GitHub Pages classroom demo ready as
the fallback.

## 11. Local validation already done

Performed without provisioning anything on Render:

- `render.yaml` validates against Render's published schema
  (<https://render.com/schema/render.yaml.json>, JSON Schema 2020-12; a
  deliberately broken copy is rejected).
- Static build with `LABSENTINEL_BASE_PATH=/`: assets at `/assets/…`, the
  configured https API compiled in; the build guard blocks an unset, http,
  local or placeholder API URL.
- Docker image built; started exactly as Render does (`python -m app.serve`,
  `PORT=10000`, Render-style `postgresql://` `DATABASE_URL`) against an empty
  Postgres 16 database:
  - migrations ran 0001 → 0007 before the server bound;
  - health 200; no data seeded;
  - readiness NOT READY with the fix for each item.
- One-time §6 sequence against that database: `app.seed`, then
  `app.demo.prepare` → **READY**, over HTTP too, with no secrets in the
  response.
- Container restart: no migration re-run, identical data, no reseeding.
- CORS: the configured https origin is allowed; any other origin (including
  localhost) gets no `Access-Control-Allow-Origin`.
- Endpoint gating matches §2 in all three configurations; `APP_ENV=production`
  with `DEMO_ENDPOINTS_ENABLED=true` refuses to start.
- A root-path build against that stack (with a static server that falls back
  to `index.html`, like the Render rewrite):
  - every route loads on direct navigation and refresh, and unknown paths show
    the in-app 404;
  - the 36 frozen classroom views are identical to the reference walk, with
    Day 1–5 at 0 / 24 / 50 / 74 / 87.
